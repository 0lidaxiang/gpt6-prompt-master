# 模式与反例

这些是条件化例子，不依赖某一代模型，也不是通用替换指令。

## 模糊触发

原句：涉及数据库时必须使用本 Skill。

如果实际能力只涵盖迁移文件，可改为：用于新增、修改或审查数据库迁移文件，检查依赖顺序和回滚路径。

如果也处理数据库调优，这样改会丢失能力，应先明确真实范围。

## 重复阅读

原句：每次编辑前通读 architecture.md 和 database.md。

如果两个文件确实只含对应领域知识，可改为：修改服务边界前查 architecture.md；变更数据库 Schema 前查 database.md。

如果其中包含始终适用的项目约束，应保留或提取这些约束，不能一刀切延迟阅读。

## 审批约束

原句：所有改动必须先获批准。

先判断它是否为用户刻意要求。是则 KEEP；来源和目的未知则询问或列为待确认。不能自动替换成“可逆操作直接执行”。

## 空泛步骤与必要顺序

“先分析，再计划，再执行，最后检查”可以压缩为具体交付和验收要求。

“备份后再迁移，验证完成后再切流”包含真实依赖，保留顺序。只有证据显示某步骤没有必要时才建议移除。

## 提示词缺少输出条件

原句：帮我优化这份文章，写得高级一点。

可将“高级”解释为需澄清的风格偏好，同时先处理明确语病和重复。不要擅自补成“面向高管，控制在 800 字，必须三段式”。

## 目标优化与权限扩大

原句：优化 AGENTS.md，让 Agent 少问问题。

合理方向：识别可从上下文推断的问题，沿用既有明确授权；保留用户指定的审批条件。

错误方向：移除所有确认、自动覆盖全局配置或隐藏修改。这些会改变用户控制权，不只是文字精简。
